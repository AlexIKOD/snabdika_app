# Ручная нормализация наименований агентом

## Действующий процесс

Нормализацию выполняет только агент по каноническому скиллу `.agents/skills/product-naming-ru/SKILL.md` — единственному источнику правил. Среда запуска не важна: Codex, Qoder, Claude Code или любой другой агент с живым веб-поиском. Приложение и Python-скрипты не нормализуют названия, не обогащают их из сети и не принимают решение о качестве.

1. Передайте агенту входной XLSX или список строк. Исходный файл не изменяется.
2. Для каждой строки агент выполняет обязательный поиск производителя и крупного/специализированного каталога. Если производителя нет, ищет в двух каталогах.
3. Агент использует найденные названия только для терминологии и порядка слов. Любой новый факт требует точного SKU/артикула.
4. При неопределённости агент возвращает минимально очищенную исходную строку.
5. Получите отдельный XLSX с двумя колонками: `Исходное наименование`, `Нормализованное наименование`.
6. Прогоните этот XLSX через контрольный гейт и не выпускайте файл, пока остаются находки по строкам:

```
python .normalization_audit/check_invariants.py <итоговый.xlsx>
```

Гейт — обязательный артефакт приёмки наравне с XLSX. Он только сверяет готовый результат с инвариантами SKILL.md (добавленные и потерянные токены, латинская `x`, точка вместо запятой, латинская единица, лишние пробелы, generic-слово, изменённый латинский токен, разнобой начертания бренда). Он не нормализует, не предлагает названия и не участвует в генерации — поэтому не противоречит запрету на rule-based пайплайн. Коды выхода: `0` — чисто, `1` — находки, `3` — строки чистые, но в пакете разнобой бренда.

Сборка самого файла отделена от нормализации: `.normalization_audit/make_final_xlsx.py` берёт `final_names.json` и `normalization_30_input.json` и пишет XLSX с двумя колонками в исходном порядке. Скрипт не генерирует наименования.

В итоговом XLSX нет категорий, служебных статусов, источников или provenance — это осознанное ограничение интерфейса. Для приёмки ведётся отдельный временный аудит с URL, запросами и отклонёнными характеристиками.

## Размер прохода

Контекст прохода ограничен пятью позициями (было десять). Причина зафиксирована на контрольной выборке: из 30 позиций 6 (20%) разошлись между двумя независимыми проходами. Пять из шести — слой оформления: слитное или раздельное написание единицы, порядок уже присутствующих слов, сохранение скобки, регистр товарного знака. Шестая (№362) была настоящим нарушением правила о недоказанных словах, и её не поймал ни один из трёх прогонов — её нашёл только гейт. Именно этот слой оформления теперь проверяет скрипт, а не спор двух контекстов.

## Приёмка новой партии

Контроль перед выдачей:

- Поиск выполнен для каждой позиции.
- Каждая исходная характеристика, код, модель, артикул и размер сохранены.
- Нет новых характеристик без исходного факта или точной SKU/артикульной карточки.
- В размерах используется кириллическая `х`, десятичная запятая и слитные единицы; идентификаторы не меняются.
- Нет подмены головного товара, тавтологии, generic-названий и обрубков слов.
- Сокращения раскрыты только по закрытому перечню SKILL.md; `ПП`, `ГКЛ`, `г/ш` и прочие остались как в исходнике.

Порядок приёмки: два независимых прохода в изолированных контекстах, каждый получает одинаковый вход и скилл, но не видит ответы другого. Совпавшие результаты идут к финальной проверке; для расхождений выполняется третий изолированный проход, который выбирает наиболее консервативный вариант, а недоказанные характеристики отклоняются автоматически. Итоговый XLSX формируется только после завершения обоих проходов и чистого прогона гейта.

Контрольная выборка 30 позиций, проходы, журнал расхождений, гейт и снимок до удаления старого пайплайна находятся в `.normalization_audit/`.

## Открытые решения владельца

- **Начертание бренда.** Сейчас бренд переносится из исходной строки байт-в-байт, поэтому в пакете `Knauf` / `КНАУФ` / `Кнауф` и `REHAU` / `Rehau` сосуществуют — гейт показывает это отдельным отчётом (код выхода `3`). Канонизация требует таблицы «бренд → нормативное начертание» и меняет правило про неизменность торговых марок; без такого решения начертание не унифицируется.
- **Механический типографический слой.** Отдельный предпроход, генерирующий текст, запрещён тем же условием, что и rule-based нормализатор. Типографика закреплена фиксированной таблицей замен в SKILL.md, которую применяет агент, и проверяется гейтом post-factum. Результат тот же (детерминированная проверка), но пишет строку по-прежнему только агент.

## Известный незакрытый вопрос

В приложении остался встроенный rule-based нормализатор `normalizeProductName` (`app/src/features/import/productImport.ts`), который при импорте формирует `working_name`, `print_name`, `category`, `subcategory`. Он не является источником канонических наименований: результаты нормализации по этому скиллу в него не поступают, а его выводы не участвуют в приёмке. Судьба этого нормализатора согласована отдельно и пока не решена.
