**Наименование собирает агент, у которого загружен скилл `product-naming-ru`, и он же выполняет

Агент выполняет по скиллу, без внешних посредников:

| Шаг | Пункт скилла |
|---|---|

| 8. Пометить `needs_review` с кодированной причиной | §1.7 |
| 9. Выпустить по схеме stage → gate → publish | §5.7 |

**Ни один шаг не делегируется отдельному программному слою.** Скрипт валидации, который упоминает
§4 скилла, — это **инструмент в руках агента** (агент его запускает и читает результат), а не
самостоятельный субъект, принимающий решения о выпуске. Разница принципиальная: сейчас решение
«выпуск прошёл» принимал `release.py`, поэтому 3 тавтологии и 5 сокращений уехали в прод
со `status = passed`.

**Что происходит с конвейером:** выводится из эксплуатации как исполнитель. Модули
`render.py`, `classifier.py`, `facts.py` перестают формировать имя. Модули, дублирующие процесс
скилла (`identity_matcher.py`, `evidence_store.py`, `release.py`, `audit_strict_qa.py`),
либо удаляются, либо понижаются до вспомогательных скриптов, которые агент вызывает по своему
усмотрению. Решение об их судьбе — результат этапа 1 (§7 п. 8).

Второй эшелон (разрешён): `r66`, `r85`, `r11`, `r244`, `r193`, `r42`, `r170`.
Обоснование замены любого `rank` — письменно в отчёте.

### 6.2. Часть A — по каждому наименованию зафиксировать

1. `rank`, `raw_name`, `name` — дословно.
2. `evidence_mode`, `research_outcome`, `matched_rule_ids`, `review_reason` — дословно из parquet.
3. Обогащённые факты с провенансом: `fact_kind`, `value`, `source_url`, `source_name`,
   `match_basis`, `source_identifier` (из `enrichment_evidence` или `accepted.jsonl`).
4. Нарушенные пункты `product-naming-ru-SKILL.md` — **номером пункта**, не пересказом.
5. Вердикт по каждой применимой гипотезе H1–H12.
6. Итог: «приемлемо» / «неприемлемо» + одна фраза почему.

### 6.3. Часть B — собрать наименование агентом со скиллом

**Агент выполняет процесс скилла целиком. Ни один шаг не делегируется программному слою.**

Порядок, обязательный для каждого из 10 наименований:

1. **Загрузить скилл** `product-naming-ru` (установлен в `.workbuddy-ai/skills/product-naming-ru/`).
   Работать по §5 скилла как по процессу.
2. **Выделить головной субъект** по §1.2 и зависимые группы — до всякой классификации.
3. **Веб-поиск.** Использовать уже собранное в `evidence_store/candidates.jsonl` (155 кандидатов)
   и при необходимости выполнить новый поиск. Отбрасывать SEO-хвост заголовков
   (после `—`/`|`: «купить», «цена», «отзывы», «интернет-магазин», «официальный сайт»).
4. **Доказать идентичность** по §5.5: факт входит в имя только при точном совпадении SKU/артикула.
   Записать, чем именно доказано (идентификатор, источник, совпадение).
5. **Собрать имя** по §2 (структура), §1.1 (анти-домысел), §1.5 (критические параметры),
   §1.6 (типографика). Два представления: `working_name` и `print_name`.
6. **Записать провенанс** каждого добавленного факта по §5.5: `fact_kind`, `value`, `source_url`,
   `source_name`, `match_basis`, `source_identifier`, `source_excerpt`, `retrieved_at`.
   Без провенанса факт в имя не попадает.
7. **Прогнать Quality Gate** скилла §4 по собранному имени — все семь проверок. Перечислить
   сработавшие и что исправлено. **Гейт блокирующий: имя не принимается, пока замечания не нулевые.**
8. **Сравнить** с текущим `name` из выпуска: лучше / хуже / равно — с обоснованием по пунктам скилла.
9. **Пометить `needs_review`** по §1.7 с кодированной причиной, если данных не хватает.

**Обязательное условие:** для каждого имени указать, какие факты взяты из исходника, какие —
из веба с провенансом, а какие **отброшены как недоказуемые**. Последнее так же важно,
как первые два.

### 6.4. Что проверить отдельно

- Прогнать Quality Gate скилла §4 по **всем 500 строкам текущего выпуска**: тавтология,

- Сколько строк нарушают §1.2 (головной субъект определён по слову внутри предложной группы)?
- Сколько строк содержат нераскрытые сокращения (`метал.`, `резин.`, `нерж.` и подобные)?

## 7. Формат отчёта

Файл: `ОТЧЁТ_Аудит_10_наименований.md` в корне проекта.

1. **Резюме** — до 15 строк.
2. **Сводная таблица 10 строк**: `rank | вердикт | нарушенные пункты | гипотезы |
   имя от агента лучше/хуже/равно`.
3. **Разбор по каждому наименованию** — структура §6.2 и §6.3.
4. **Сравнение «конвейер vs агент со скиллом»** — по 10 строкам: `raw_name`, `name` от конвейера,
   `name` от агента, вывод. Отдельно: сколько имён агент улучшил, сколько не смог.
5. **Реестр подтверждённых дефектов** — `ID | формулировка | затронуто из 10 | доказательство
   (rank + цитата) | место в коде`.
6. **Реестр опровергнутых гипотез** — с указанием, что её опровергло.
7. **Масштаб** — по каждому дефекту: сколько строк из 500 затронуто, с командой подсчёта.
8. **Судьба конвейера.** По каждому модулю `prototype/normalization/` — вердикт:
   удалить / понизить до вспомогательного скрипта / сохранить. С обоснованием, что именно
   он дублирует из скилла и почему агент справляется без него.
9. **Что осталось непроверенным** — честный список.

**Любое число — с командой воспроизведения.** Утверждения без числа запрещены.

## 8. Запреты и ограничения

1. **Не додумывать факты.** Нет провенанса — факт не входит в имя. Корректное написание,
   требующее отсутствующих данных, помечается «не выводится без додумывания».
2. **Не менять правила, контракт `product-naming-ru-SKILL.md`, `.ai-factory/rules/` и опубликованный
   выпуск.** Изменение скилла — только через канонический файл и синхронизацию трёх копий.
3. **Не удалять и не переписывать модули конвейера в этапе 1.** Вердикт по каждому — в отчёте (§7 п. 8).
4. **Эксперименты — только в `.research/`** или отдельной временной папке.
5. **Не выдавать метрики за качество.** «147 тестов проходят» и «500/500 строк» — не доказательство
   качества наименований. Доказательство — цитата имени и ссылка на пункт скилла.
6. **Не «чинить» дефект по ходу аудита.** Нашёл причину — записал, пошёл дальше.
7. Слова «полностью готово», «успешно», «значительно улучшено» без числового подтверждения
   не использовать.
