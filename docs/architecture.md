# Архитектура

Срез на 24 октября 2026 года после ввода вариантов подбора и настроек расчёта
в шапке заявки.
React 18 + TypeScript + Vite 5; Tauri 2 + Rust; локальный FastAPI-сервис
с SQLite и каталогом Parquet.

## Слои

```text
React (app/src)
  pages/            экраны и маршруты
  components/       общие и предметные компоненты
  api/client.ts     единый клиент: mock, HTTP или native-мост
  lib/format.ts     форматирование денег, дат, чисел
  styles/           tokens.css, ui.css
        │
        ├── HTTP /api (x-snab-key) ── FastAPI (app/backend)
        │                                main.py        контракт и авторизация
        │                                store.py       SQLite, заявки, операции
        │                                services/      каталог, сопоставление, счёт
        │
        └── Tauri invoke ────────────── Rust (app/src-tauri)
                                         local_api, Parquet-каталог, Credential Manager
```

## Состояние и деньги

Подтверждённая позиция хранит ревизию, хеш значимых полей, время и оператора,
локальные ID товара и поставщика, UUID/тип «МойСклад», единицу и упаковку,
количество, раздельные цены и источники. Изменение значимых полей снимает
подтверждение; для выставленных строк редактирование закрыто.

Preview хранит состав, версии, параметры и payload. До HTTP POST транзакционно
создаётся операция с уникальными preview ID / operation ID и claims исходных
строк. Объединение одинаковых строк выключено по умолчанию.

Режим расчёта, процент и НДС — один объект `pricing` на заявку. Он меняется
в шапке заявки (`POST /api/requests/{id}/pricing`), сервер пересчитывает цену
к счёту по каждой строке и отдаёт её как `sale_price`; базовая `retail_price`
не перезаписывается, поэтому пересчёт идемпотентен. Предпросмотр счёта читает
этот же объект из заявки, а не тело запроса, и сохраняет его в снимке.
Закупка включает всю закупочную стоимость, маржа считается по выручке без НДС.
Непредставимая в копейках цель блокирует отправку с видимым остатком; разница
меньше копейки не считается остатком. Убыток только предупреждает.

Повтор использует прежнюю операцию. После неопределённого исхода сервис ищет
документ по syncId и сверяет его; автоматического нового POST нет.

## Создание документа

Три пути сходятся в одну модель `ClientRequest`:

1. **Заявка клиента** — `POST /api/requests` разбивает текст на позиции;
   `POST /api/requests/{id}/match` сопоставляет их с каталогом.
2. **Каталог** — `POST /api/invoices/catalog-drafts` создаёт черновик по
   `material_ids`, клиент дописывает количество и закупку по каждой строке.
3. **ИИ-подбор** — тот же `createRequest` без клиента плюс `match`.

Дальше документ живёт в таблице позиций: инлайн-правка и подтверждение
(`PATCH .../positions/{pid}`), выбор варианта подбора
(`POST .../positions/{pid}/variant`), настройки расчёта
(`GET`/`POST .../pricing`), предпросмотр (`POST .../invoice/preview`)
и создание счёта (`POST /api/invoices`).

## Хранение

SQLite: `%LOCALAPPDATA%/Snabdika/invoices.sqlite3`; WAL и транзакции сохраняют
операции после перезапуска. Для резервной копии остановите сервис и копируйте
БД вместе с WAL/SHM. Секреты — Windows Credential Manager, service `Snabdika`.

Диагностика: `%LOCALAPPDATA%/Snabdika/logs/invoices.log`, ротация 2 МБ × 3 файла.
Тела запросов, токены и персональные данные не журналируются.

## Сборка

- `npm run backend:bundle` собирает sidecar; `tauri build` вызывает её сам.
- Release использует `backend/snabdika-backend.exe` и `_internal/`.
- Debug использует Python из `SNABDIKA_PYTHON` или `python`.

## Оставшийся контур

Распознавание изображений и файлов, рабочий импорт нового Excel, постоянный
кеш AI и безопасная запись Parquet остаются отдельными задачами. Desktop-каталог
Parquet продолжает работать через native-команды.
