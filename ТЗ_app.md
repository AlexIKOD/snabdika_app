## 1. Назначение системы

Разработать десктопное приложение для формирования единой базы строительных материалов от различных поставщиков, обработки Excel-прайсов, хранения цен и характеристик, распознавания клиентских запросов с помощью AI и создания счетов покупателю в системе «МойСклад».

Основной принцип работы:

```text
Excel-прайсы поставщиков
        ↓
Импорт и нормализация
        ↓
Единая база материалов
        ↓
Сохранённые варианты наименований поставщиков
        ↓
Parquet для быстрого поиска и анализа
        ↓
Запрос клиента текстом или изображением
        ↓
AI + локальный поиск кандидатов
        ↓
Ручное подтверждение оператором
        ↓
Счёт покупателю в «МойСклад»
```

---

## 2. Цели разработки

Приложение должно:

1. Объединять номенклатуру разных поставщиков в единую базу.
2. Распознавать разные наименования одного и того же материала.
3. Сохранять связи между названием поставщика и единым материалом.
4. Использовать сохранённые связи при повторной загрузке прайсов.
5. Обновлять цены без создания дублей материалов.
6. Хранить историю цен и источники изменений.
7. Поддерживать закупочные, розничные и другие типы цен.
8. Хранить веса, единицы измерения, коды, артикулы и характеристики.
9. Обрабатывать клиентские запросы по тексту и изображениям.
10. Использовать Gemini API для извлечения характеристик и сопоставления материалов.
11. Требовать ручного подтверждения результата AI.
12. Создавать счёт покупателю через API «МойСклад».

```text

weight_kg
length_mm
width_mm
height_mm
thickness_mm

```

Дополнительные характеристики хранятся в `attributes_json`.

### 7.2. Идентификаторы материала

Для одного материала может существовать несколько идентификаторов:

```text
- внутренний код;
- код поставщика;

```

Идентификаторы поставщиков нельзя хранить только в одном общем поле. Они должны быть привязаны к конкретному поставщику.

## 8. Варианты наименований поставщиков

Это обязательная часть системы.

Разные поставщики могут называть один и тот же материал по-разному. Все варианты должны сохраняться и связываться с единой карточкой.

Пример:

```text

Варианты:
Плита OSB-3 9х1250х2500 мм
ОСБ-3 9 мм 1250*2500
Плита ОСП 3 9x1250x2500
OSB 3 9 1250 2500
ОСБ девятка 1250 на 2500
```

## 9. Нормализация названий

Нормализация должна включать:

- перевод в нижний регистр;
- замену `ё` на `е`;
- удаление лишних пробелов;
- унификацию кавычек;
- унификацию символов `×`, `x`, `х`, `*`;
- унификацию дефисов;
- удаление служебных символов;
- нормализацию размеров;
- выделение толщины, ширины, длины и диаметра;
- нормализацию единиц измерения;
- нормализацию кодов с ведущими нулями;
- нормализацию сокращений и синонимов.

Пример:

```text
00000106004 → 106004

OSB-3 9x1250x2500
ОСБ 3 9 × 1250 × 2500
Плита OSB 3 9 1250 2500
```

должны попадать в один поисковый кластер при совпадении ключевых характеристик.

## 12. Алгоритм сопоставления при повторном импорте

При загрузке обновлённого прайса поставщика система должна использовать следующие уровни.

### Уровень 1. Идентификатор

- код поставщика;
- артикул поставщика;
- штрихкод;
- UUID;
- код «МойСклад».

### Уровень 2. Сохранённая связь

```text
supplier_id + normalized_name → material_id
```

Если такая связь ранее была подтверждена, она используется автоматически.

### Уровень 3. Точное нормализованное название

Сравниваются:

- название;
- бренд;
- размеры;
- единица измерения;
- ключевые характеристики.

### Уровень 4. Нечёткое сопоставление

Используется для небольших изменений в написании:

```text
ОСБ / ОСП / OSB
х / × / *
мм / миллиметры
```

### Уровень 5. Векторное сопоставление

Используется при отсутствии точного совпадения.

Автоматическое сопоставление запрещается при конфликте ключевых характеристик, например:

```text
OSB 9 мм
OSB 12 мм
```

## 14. Новые названия поставщика

Если поставщик изменил название товара, система не должна автоматически создавать дубль.

Пример:

```text
Старое:
Плита OSB-3 9х1250х2500 мм

Новое:
ОСП-3 9 мм 1250*2500
```

Система должна:

1. найти наиболее вероятный существующий материал;
2. показать оператору найденный вариант;
3. отобразить уровень уверенности;
4. показать отличия характеристик;
5. запросить подтверждение;
6. сохранить новое название как alias.

После подтверждения новое название автоматически распознаётся при следующих импортах.

## 17. Хранение на Яндекс Диске

Приложение рассчитано на одного оператора.

Рабочая схема:

```text
Яндекс Диск
    ↓ синхронизация
Локальная рабочая папка
    ↓
SQLite + локальный векторный индекс
    ↓
Parquet и резервные копии на Яндекс Диск
```

Структура:

```text
Snabdika_app
├── database
│   ├── catalog_materials.parquet
│   ├── supplier_offers.parquet
│   ├── price_history.parquet
│   └── material_aliases.parquet
├── imports
├── backups
├── images
├── vectors
└── logs
```

SQLite не рекомендуется постоянно открывать непосредственно с Яндекс Диска. Приложение должно работать с локальной копией и синхронизировать результаты.

## 19. AI-сопоставление

### 19.1. Общая схема

```text
Текст или изображение клиента
        ↓
OCR и извлечение характеристик
        ↓
Поиск по коду и alias
        ↓
Нечёткий поиск
        ↓
Векторный поиск top-K кандидатов
        ↓
Gemini API получает запрос и кандидатов
        ↓
Структурированный результат
        ↓
Ручное подтверждение оператора
```

В Gemini не должна передаваться вся база материалов. Сначала backend формирует ограниченный список кандидатов.

### 19.2. Извлекаемые поля

```text
request_text
product_name
quantity
unit
brand
article
code
length_mm
width_mm
height_mm
thickness_mm
diameter_mm
color
additional_attributes
```

### 19.3. Формат ответа AI

```json
{
  "items": [
    {
      "request_text": "ОСБ девятка 1250 на 2500",
      "quantity": 20,
      "unit": "шт",
      "candidate_material_id": "MAT-00001245",
      "confidence": 0.96,
      "reason": "Совпадают толщина и размеры",
      "extracted_attributes": {
        "thickness_mm": 9,
        "width_mm": 1250,
        "length_mm": 2500
      }
    }
  ]
}
```

Если материал не найден:

```json
{
  "candidate_material_id": null,
  "confidence": 0.21,
  "status": "not_found",
  "reason": "Недостаточно данных"
}
```

AI не имеет права самостоятельно создавать материал или подтверждать его без оператора.

## 20. Ручное подтверждение

Оператор должен видеть:

- исходный текст запроса;
- изображение;
- распознанные характеристики;
- предложенное наименование;
- код;
- артикул;
- поставщика;
- закупочную цену;
- розничную цену;
- вес;
- единицу измерения;
- уверенность AI;
- альтернативные варианты.

Действия:

```text
Подтвердить
Выбрать другой вариант
Найти вручную
Создать alias
Изменить количество
Разделить позицию
Добавить материал
Отклонить позицию
```

Счёт нельзя формировать, пока все позиции не подтверждены или явно не исключены оператором.

## 26. Безопасность

1. API-ключи не хранить в открытом `config.json`.
2. Секреты не должны передаваться во frontend.
3. Не записывать токены в логи.
4. Использовать системное хранилище Windows или зашифрованный vault.
5. Все SQL-запросы выполнять параметризованно.
6. Проверять тип и размер загружаемых файлов.
7. Ограничить размер изображений перед отправкой во внешний API.
8. Не отправлять во внешний AI всю базу материалов.
9. Хранить минимально необходимый объём данных во внешних API.
10. Добавить кнопку удаления локальных запросов и изображений.

Ключи API должны задаваться через локальные настройки или переменные окружения и не должны включаться в репозиторий и техническое задание.

## 28. Критерии приёмки

Система считается готовой к первой эксплуатации, если:

1. Загружает все предоставленные Excel-файлы.
2. Позволяет настроить профиль каждого поставщика.
3. Создаёт единую карточку материала.
4. Сохраняет несколько названий одного материала.
5. При повторной загрузке узнаёт ранее импортированный материал.
6. Обновляет цены без создания дублей.
7. Сохраняет историю изменения цен.
8. Формирует Parquet-файлы каталога и прайсов.
9. Находит материал по клиентскому тексту.
10. Принимает изображение клиентского запроса.
11. Передаёт изображение и список кандидатов в Gemini API.
12. Показывает результат оператору.
13. Не позволяет создать счёт без подтверждения позиций.
14. Создаёт счёт покупателю в «МойСклад».
15. Не создаёт дубли при повторной отправке.
16. Восстанавливает работу после ошибки импорта.
17. Не блокирует интерфейс во время длительных операций.
18. Не хранит секретные ключи в исходном коде и открытом конфиге.
