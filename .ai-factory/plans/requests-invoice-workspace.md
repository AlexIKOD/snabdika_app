# Спецификация: раздел «Заявки» как рабочее место формирования счетов

Создана: 21 октября 2026 года, Europe/Moscow.
Статус: **согласована с пользователем; готова к декомпозиции на задачи**.
Источник: сессия grilling (все вопросы согласованы 21.10.2026).
Тикеты: `.scratch/requests-invoice-workspace/issues/` (01–10).
Границы: только фронтенд на существующем API; бэкенд и моки не изменяются.

## Проблема

Сейчас раздел называется «Запросы клиентов» и фактически является реестром
клиентских заявок. Внутри него детальный экран показывает каждую позицию
крупной карточкой на всю ширину: заголовок, AI-обоснование, раскрывающийся
блок из семи полей цены, чипы поставщиков. На заявке из 20–40 строк оператор
прокручивает несколько экранов и не может сравнить позиции глазами.

Второй путь создания счёта — сборка из внутреннего каталога — живёт внутри
раздела «Счета» в виде композера: поиск, кнопки «Добавить {id}» и
«Убрать {id}», без количества, без цен, в узкой прокручиваемой области.
Количество и цены вводятся уже на другой странице, повторно. Раздел «Счета»
одновременно пытается быть и реестром, и местом создания документов.

Третий путь — ИИ-подбор по свободному описанию — в интерфейсе отсутствует
как самостоятельный сценарий.

Итог: чтобы выставить счёт, оператор проходит три разных экрана, вводит
количество дважды и не видит, какие строки готовы, а какие блокируют счёт.

## Решение

Раздел переименовывается в «Заявки» и становится рабочим местом, где счёт
рождается: три явных способа начать документ и один экран работы с позициями.
Раздел «Счета» остаётся реестром уже созданных документов.

Три способа создать документ на отдельной странице входа:

1. **Распознать заявку клиента** — клиент, номер, вставка текста; строки
   становятся позициями и сопоставляются с каталогом через ИИ.
2. **Собрать из каталога** — поиск по внутренней базе, корзина с количеством,
   создание черновика из выбранных материалов.
3. **ИИ-подбор по описанию** — свободный текст без клиента; тот же механизм
   сопоставления, что и в первом способе.

Позиции отображаются плотной таблицей с инлайн-правкой количества, цен и
поставщика; раскрытие строки используется только для чтения и редких действий.
Подтверждение строки — одна кнопка, внутри которой сохранение полей и
подтверждение выполняются последовательно. Готовность документа к счёту видна
счётчиком и фильтром, а «Создать счёт» берёт выбранные строки либо все готовые.

## Решения по реализации

### Навигация и именование

- Раздел называется «Заявки»; маршруты `/requests` и `/requests/:id` сохраняются.
- Новый маршрут страницы входа — `/requests/new`; `Ctrl+N` ведёт туда.
- Переименование затрагивает: навигацию, палитру команд, справку горячих клавиш (Alt+5), заголовки страниц, пустые состояния, тексты ошибок.
- Раздел «Счета» сохраняет маршрут `/invoices`.

### Страница «Заявки» (список)

- Список рабочих документов, не реестр заявок.
- Колонки: номер, клиент, источник, позиций, готово к счёту, сумма, статус, дата, действия.
- Источник — вычисляемое представление: «Заявка» с номером документа, «Каталог», «AI».
- Для документов из каталога клиент отображается как «—».
- Фильтр-чип «Скрыть выставленные»; пустое состояние объясняет три способа создания.
- Удаление с подтверждением; документ со связанным счётом удалить нельзя (правило бэкенда, UI показывает причину).

### Страница входа

- Отдельная страница, три режима, переключаемые без перезагрузки.
- Режим «Распознать заявку»: клиент, номер (автогенерация, редактируемый), текст; каждая непустая строка — позиция.
- Режим «Собрать из каталога»: поиск, результаты, корзина, создание черновика.
- Режим «ИИ-подбор по описанию»: тот же ввод текста без клиента; после создания доступна кнопка сопоставления.
- После создания документа — переход на его таблицу позиций.

### Корзина каталога

- Количество — количество в счёте (то же поле, что попадает в счёт), единица — из карточки материала, только для чтения.
- Дубликаты материалов в корзине не допускаются.
- Создание: вызов существующей операции создания черновика из каталога, затем параллельная запись количества по каждой позиции.
- Если запись количества по строке не удалась, документ всё равно открывается, а строка остаётся без количества с явной пометкой.
- Корзина живёт только до создания черновика; после создания состав меняется через «+ Из каталога» в таблице.

### Таблица позиций

- Новый компонент таблицы позиций; существующая универсальная таблица приложения не расширяется инлайн-редактированием.
- Колонки: номер строки, клиент, товар из каталога, количество с единицей, цена продажи с маржой, закупка, поставщик, статус с уверенностью, действия. Колонка действий закреплена справа.
- Инлайн-правка: количество, цена продажи, закупка, поставщик.
- Действия в строке: подобрать материал, разделить, удалить, подтвердить/снять подтверждение.
- Раскрытие строки (одно одновременно): AI-обоснование, вопросы проверки, флаги, альтернативные предложения поставщиков, «Разделить строку».
- «+ Из каталога» добавляет материал в текущий документ с уже заполненными полями сопоставления.
- Наименование клиента показывается полностью в подсказке при усечении.

### Подтверждение строки

- Одна кнопка «Подтвердить». Внутри: сохранение изменённых полей, затем отправка подтверждения.
- Кнопка показывает индикатор и блокируется на время операции (обращение к «МойСклад»).
- Ошибка валидации отображается в строке, без тоста.
- Требования бэкенда, которые нельзя обойти: выбранный материал, количество больше нуля, единица совпадает с единицей каталога, цена продажи больше нуля, закупка больше нуля, оба источника цены непустые.
- Любая правка значимого поля на подтверждённой строке возвращает её в «Требует проверки» и снимает подтверждение; UI показывает это сразу, без тоста.
- «Снять подтверждение» доступно отдельным действием.

### Цены и источники

- Закупка подставляется из лучшего предложения поставщика; источник формируется автоматически с названием поставщика и датой прайса, если она доступна.
- Цена продажи вводится вручную. Если у материала есть розничное предложение, доступно действие «взять розницу из прайса».
- Источник цены продажи — список типовых значений с возможностью свободного ввода.
- Маржа по строке считается на лету; отрицательная маржа выделяется.
- Строка без цены продажи помечается и не участвует в сборке счёта.

### Готовность и создание счёта

- В паспорте документа — «Готово к счёту: N из M».
- В тулбаре — переключатель «Только требующие внимания».
- «Создать счёт» берёт выбранные строки; если ничего не выбрано — все готовые.
- Неактивная кнопка объясняет причину: нет готовых строк, не заполнены цены, не подтверждено количество.
- Дальше используется существующее окно предпросмотра и создания счёта без изменения его логики.

### Массовые действия

- Тулбар над таблицей: «Подтвердить все > 90%», «Выбрать мин. закупку», «Отклонить ненайденные».
- Чекбоксы строк управляют массовым подтверждением и удалением.
- Массовое подтверждение выполняется последовательно по строкам и сообщает итог: сколько подтверждено, сколько отклонено валидацией.

### Раздел «Счета»

- Только реестр: таблица, фильтры, экспорт, шторка состава.
- Композер каталога удаляется со страницы; кнопка создания ведёт на страницу входа в режиме каталога.
- Колонка «Запрос #id» заменяется на «Источник» со ссылкой на исходный документ.
- Добавляются фильтр по периоду и переключатель «Только убыточные».
- Локальные черновики и ошибки отправки показываются с явными бейджами.
- В шторку добавляется «Открыть исходный документ».

### Стиль

- Используются существующие токены и компоненты; новые зависимости не добавляются.
- Новые визуальные паттерны (плотная таблица с инлайн-полями, панель выбранных, sticky-итоги) собираются из существующих классов; недостающее добавляется точечно.
- Тёмная и светлая темы остаются рабочими; состояния фокуса и клавиатурной навигации обязательны.

### Этапы

1. Раздел «Заявки»: страница входа, корзина, таблица позиций, подтверждение, создание счёта, переименование.
2. Раздел «Счета»: удаление композера, «Источник», период, убыточные, шторка.

Второй этап начинается после самостоятельного тестирования первого и подтверждения пользователем.

## Решения по тестированию

Хороший тест проверяет наблюдаемое поведение страницы и не завязан на внутреннюю структуру компонентов: он ищет элементы по роли и доступному имени, работает через мок API-клиента и не проверяет классы или порядок вызовов сверх необходимого.

Шов — уровень страниц: рендер через `MemoryRouter`, мок `apiClient`. Новые швы не создаются; компонентные тесты допускаются только там, где страницу целиком не отрендерить (корзина каталога).

Проверяемые модули:

- страница списка документов: колонки, источник, готовность, скрытие выставленных, удаление с подтверждением;
- страница входа: три режима, блокировка создания без обязательных полей, переход на документ;
- корзина каталога: поиск, добавление, дубликаты, количество, создание черновика и запись количества;
- таблица позиций: инлайн-правка, потеря подтверждения при правке, раскрытие строки, «+ Из каталога»;
- подтверждение: последовательность сохранения и подтверждения, показ ошибки валидации в строке, индикатор;
- создание счёта: выбор строк, готовые строки, причина блокировки;
- реестр счетов: источник, фильтры периода и убыточности, отсутствие композера.

Существующие тесты проекта (`requestWorkflow`, `catalogInvoice`, `invoices`, `liveInvoice`, `requests`) — приоритетный образец стиля; тесты, завязанные на удалённый композер и карточки позиций, переписываются под новый интерфейс.

Проверки перед сдачей этапа: `npm run test`, `npm run lint`, `npm run build`. UI/UX проверяется самостоятельно в браузере на dev-сервере: три сценария входа, подтверждение, частичный счёт, реестр. Бэкенд-тесты запускаются только если бэкенд менялся.

## Вне рамок

- Изменения бэкенда, мок-сервера и схемы данных.
- Качество ИИ-сопоставления и его промпты.
- Распознавание файлов и изображений (остаётся недоступным, UI это сообщает).
- Переработка окна предпросмотра счёта, режимов расчёта, НДС и реквизитов «МойСклад».
- Изменение правил сборки счёта и валидации подтверждения.
- Редактирование ТЗ (`ТЗ_app.md` и связанные документы).
- Сборка установщика, native-окно, sidecar.
- Переименование раздела в базе знаний и внешних документах.

## Дополнительные заметки

- Универсальная таблица приложения не поддерживает инлайн-редактирование, поэтому таблица позиций — новый компонент. Это единственное место, где объём кода может оказаться больше ожидаемого.
- Подтверждение позиции обращается к «МойСклад»; в тестах этот вызов мокируется, иначе сценарий падает на сети.
- Создание черновика из каталога создаёт новый документ на каждый вызов; поэтому корзина недоступна после создания, а состав расширяется через добавление позиции.
- Количество записывается в позиции отдельными запросами после создания черновика; частичный сбой не должен блокировать открытие документа.
- Правка количества или единицы на бэкенде сбрасывает отметки сверки; UI обязан показывать это явно, а не молча.
- Значения источников цены — свободные строки; список типовых значений только подсказывает.
